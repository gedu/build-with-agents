# An instruction whose origin cannot be located cannot be reconciled — only obeyed or broken

**The claim.** Agent instructions arrive from many layers at once. Systems routinely document
**precedence** — which layer wins a conflict. They routinely fail to document **provenance** —
where a given instruction physically came from. Precedence alone is not enough: it resolves which
rule applies, but it gives an agent no way to *change* the losing rule, report it, or verify it
still exists. Without provenance, a conflicting instruction can only be obeyed or violated.

## The evidence

Verified first-hand on 2026-08-05, Claude Code with `claude-opus-5[1m]`.

An active session directive stated: *do not call the Agent tool unless the user requested it.* A
project-level contract required review lenses to run as sub-agents. The two were jointly
unsatisfiable, so locating the directive's source became necessary to resolve it.

Searched, and **not found in any of them**:

| Location searched | Result |
|---|---|
| `AGENTS.md` (project root instructions) | absent |
| Project `.claude/settings.json` / `settings.local.json` | absent — no project settings file existed |
| User `~/.claude/settings.json` | absent |
| Files generated by `gentle-ai` | absent |
| The `engram` plugin source | only a coincidentally-named `agentTools` Go variable |

The instruction was demonstrably active — it appeared in the agent's own operating context — and
simultaneously unlocatable in the configuration surface available to that agent.

## What the missing provenance actually cost

The failure was not the conflict. Conflicts are ordinary. The failure was that the conflict could
not be traced, and four consequences followed, in order:

1. **Misattribution.** The conflict was attributed to `gentle-ai`, the tool whose contract was on
   the losing side. It was reported as an upstream defect.
2. **A wrong expectation.** Because it was believed to be an upstream bug, the resolution was
   expected to arrive in a future release. No release could have affected it.
3. **Repeated bypasses.** Three commits shipped without a review receipt in one day, each
   individually documented and each resting on the same misdiagnosis.
4. **Resolution by fiat rather than by fix.** It was closed by ratifying
   `decisions/0008-review-lenses-may-use-subagents.md` — an authority statement that overrides the
   directive — because the alternative, editing the emitting file, was unavailable. The directive is
   still there. Nothing was repaired; something was outranked.

Note the shape of point 4: **an unlocatable rule can only be overruled, never corrected.** Every
such resolution adds a layer instead of removing one, so the instruction surface grows
monotonically and each new conflict is harder to trace than the last.

## Why this is a design constraint, not an incident

Instructions reach an agent from at least: the model's system prompt, session or harness
configuration, output-style or persona layers, project instruction files, nested instruction files,
plugin-injected text, tool- and MCP-server-provided instructions, skill definitions, and generated
files that are themselves derived from other files.

Any layer that injects behavior-shaping text and does not identify itself creates the failure above.
Two properties make an instruction surface debuggable:

- **Self-identification** — an instruction states, or can be traced to, the file or mechanism that
  emitted it.
- **Enumerability** — the active set can be listed. "What rules am I currently operating under, and
  from where" should be answerable, not reconstructed by search.

A system with documented precedence and undocumented provenance will feel well-specified right up
to the first conflict, and then be undebuggable.

**Enumerability partly exists in this harness, and an earlier draft of this file wrongly said it did
not.** Anthropic's own architect guide documents a `/memory` command for verifying which memory files
are loaded and diagnosing inconsistent behavior across sessions
(`research/claude-certified-architect-exam-guide.md`). That is a real implementation of the property,
and it was **not used** during the search recorded above — a gap in that investigation, not in the
harness.

What the correction leaves standing is narrower and more precise: enumeration covers **memory files**
— the `CLAUDE.md` hierarchy and imported rule files. The directive in this case was not a memory
file; it arrived at the session or harness layer, which no documented command enumerates. So the
defect is not "no enumeration exists" but **enumeration covers one layer of a many-layer surface**,
and a conflict originating in an uncovered layer is still untraceable. Coverage, not absence, is the
gap.

## Scope

One harness, one day, one conflict. The **mechanism** is general to any multi-layer instruction
system, and the cost sequence above is a consequence of the structure rather than of this
implementation. No claim is made about how frequently this occurs, in this harness or any other —
that would need a survey nobody here has run.

Note also that this file cannot demonstrate the *absence* of provenance in general, only that it was
absent in one traceable case. The four-step cost sequence is the transferable part.

## What would sharpen it

Attempt the same trace on a second harness with a deliberately conflicting instruction, and record
whether the emitting layer is identifiable. That turns a single case into a comparison.
